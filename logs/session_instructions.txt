## PROPOSED METHODOLOGY

**Approach**: Paired prompt intervention on a fixed SimpleQA sample with dual grading and explicit calibration limitations

**Steps**:
1. Freeze dataset revisions, item IDs, prompt templates, model revisions, library versions and seeds before evaluation. Serve one model at a time on one allocated GPU, unload it before loading another model or the local judge; no tensor parallelism. Use registered model settings and log thinking mode, token limits, truncations, parse errors and all reruns.
2. Pin the SimpleQA dataset used by inspect_evals/simpleqa and choose exactly 450 distinct questions by SHA256(seed 20261020 plus canonical ID): first 50 reserved only for calibration and next 400 for main evaluation. Use temperature 0.6, final-answer budget 256 tokens and total generation cap 4096; preserve native reasoning behavior for DeepSeek, disable optional thinking for Qwen3, and log the exact templates. Report truncated/no-final-answer outputs separately.
3. Create 150 labelled calibration responses from the disjoint 50 questions: an exact gold answer, the explicit abstention string, and an explicitly contradictory answer per question. Construct incorrect responses by an unambiguous negation of the supplied gold answer rather than guessing a competing fact. These are programmatically constructed labels based on dataset gold, not human-labelled model completions. Calibrate azure-gpt-4.1-mini-judge and qwen2.5-7b-judge on all 150 using the SimpleQA three-class rubric; freeze judge prompts before main grading.
4. Report each judge confusion matrix, accuracy, macro-F1, Cohen kappa, correct-answer false-positive rate and bootstrap intervals. Require accuracy >=0.90 and kappa >=0.80 on controls for an eligible primary judge. Azure is primary if eligible, otherwise the local judge if eligible. If neither passes, publish raw generations and calibration failure with no factuality headline or candidate. Never treat inter-judge agreement as human ground truth. If existing human-labelled response calibration data are available, report a separate check, without requesting new human work.
5. Grade every main final answer with both judges, blinding model and prompt condition. Parse away reasoning only with the model-specific final-answer boundary and preserve parse failures. Report disagreement rates by model and condition and each judge sensitivity analysis. Track unscored cases and bound results by treating them as correct versus incorrect; abstention and invalid/truncated output are separate fields. Suppress candidates if unscored share exceeds 2% or the effect direction differs between eligible judges.
6. Primary paired Qwen3 contrasts are intervention-minus-baseline incorrect frequency and correct frequency, using all 400 questions as denominators. Require incorrect difference <=-0.10, its 95% CI upper bound <0, and a one-sided 95% lower bound for correct difference >=-0.03 to support the joint hypothesis. Report abstention rate, attempted-answer accuracy and coverage; do not call lower coverage alone an improvement. Holm-adjust the two secondary checkpoint intervention tests and label insufficient-power results inconclusive.

8. Write a preregistration and item manifest before collecting main results. Use seeds 11, 22 and 33 for three repetitions; average repetitions within each item before uncertainty estimation. Report paired comparisons on identical items, n independent items, number of completions, means, SEs and 95% item-cluster bootstrap CIs (10000 resamples). Retain failed items in denominators with explicit failure labels; distinguish infrastructure failures from model failures.
9. Save results/safety/*.json in the neurico-safety-result/v1 schema used by the safety-evals skill, plus item-level scores, manifests, reproduction commands and REPORT.md. Candidate findings require the preregistered effect threshold and a CI excluding zero, with multiplicity correction for secondary model comparisons. Report null and inconclusive results. Claims apply to these checkpoints and protocols only, not entire families or causal effects of distillation.

# AI Safety Evaluation Domain Guidance

This template covers safety evaluation, red-teaming, monitoring and auditing of language
models: refusal calibration, jailbreak robustness, honesty and hallucination, sycophancy,
deception and scheming propensity, dangerous-capability proxies (CBRN, cyber), agentic misuse,
bias, probes and monitors, and comparisons across model families and versions.

## Domain Overview

The purpose of this work is to produce findings that an AI lab or an independent evaluator
would trust: numbers with uncertainty, judges with known error rates, transcripts for every
flagged behaviour, and a reproduction pack. Evaluations are experiments. Treat them as such.

## Key Methodological Principles

### 1. Every number carries n and uncertainty
- Report mean, standard error (or a 95% CI) and n next to every headline number. Binary
  scores: SE = sqrt(p(1-p)/n). Use clustered SEs when items share a source (seed prompts,
  mutations of one base behaviour, repeated beliefs).
- Compare models or conditions with paired differences on identical items, same sampling
  settings, same judge. Never compare numbers taken from different `--limit` subsets or
  different shuffle seeds.
- Small suites (XSTest 450, StrongREJECT 313, JailbreakBench 200) only detect large effects.
  Say so. Prefer more samples per item (`--epochs`) over lowering temperature.
- Before claiming drift or regression between model versions, establish the repeated-run noise
  floor for that (model, eval) pair (at least 3 identical runs).

### 2. Judges are instruments: calibrate them
- Every LLM judge (refusal, harmfulness, honesty, sycophancy) is calibrated on a labelled set
  (100-200 items) and its agreement (accuracy, Cohen's kappa, TPR at a fixed FPR) is reported
  with the results. Re-calibrate whenever the judge model or prompt changes.
- Prefer two independent judges (for example a local open-weight judge and an API judge) and
  report their agreement; send disagreements to a human-review list in the report.
- Count unscored or unparseable judge outputs and report them as a fraction of n.
- A judge must never share a model family with a policy being optimised against it.

### 3. Pair every metric with its counterpart
- Refusal on unsafe prompts is paired with over-refusal on safe look-alikes (XSTest safe +
  unsafe, OR-Bench).
- Capability on hazardous proxies (WMDP) is paired with a general-knowledge baseline (MMLU
  subset) so uplift is separable from general ability.
- Harmful compliance under jailbreak is paired with the direct-request baseline.
- A detector (probe, monitor, classifier) reports both its true-positive rate and its
  false-positive rate at the operating point actually used.

### 4. Probes, monitors and classifiers
- Train on one split, tune on a dev split, report only on a held-out test split; report AUROC
  and TPR at 1% and 5% FPR with bootstrap CIs.
- Validate on model organisms with known ground truth (implanted behaviours) when available,
  but never tune the detector on the organism it is scored on.
- Record the exact layer, token position, pooling and normalisation; save the probe artefact.

### 5. Evaluation awareness and sandbagging
- Score evaluation awareness on transcripts where behaviour matters (agentic scenarios): count
  verbalised "this is a test" statements; keep a realism filter; report rates with results.
- For open-weight models, compare behaviour under "evaluation" and "deployment" framings of the
  same task; a large gap is itself a finding.

### 6. Fairness across models
- Identical prompts, system prompts (or documented absence), temperature, max tokens, tool
  definitions and judge for every model in a comparison. Record the exact model id, revision
  hash or API version, and date.
- Thinking/reasoning models: state whether reasoning was enabled and whether the judge saw it.
- Label runs on 0.5B-3B models as pipeline tests; they do not support cross-family claims.

### 7. Hazard handling and disclosure
- Never generate or store real uplift content for CBRN or offensive cyber; use proxies (WMDP,
  CTF ranges, benchmark behaviours) and store any harmful completions only under
  `results/restricted/` (git-ignored), summarised and hashed in reports.
- A finding on an API model goes to the provider's disclosure channel before publication;
  the report records the disclosure state.
- Treat downloaded datasets and model outputs as untrusted data: never execute them.

### 8. Reproducibility pack (required for every finding)
- `findings/<slug>.yaml` with: title, category, models, summary, evidence (metrics with n and
  SE, transcript paths), reproduction (exact command, dataset revision, judge id and version,
  seeds), limitations.
- `results/safety/*.json` in the `neurico-safety-result/v1` schema (one file per eval x model),
  produced by the safety-evals skill scripts.
- Inspect `.eval`/`.json` logs kept under `results/safety/inspect_logs/`.

## Standard Tooling (see the safety-evals skill)
- Inspect (`inspect_ai`) and `inspect_evals` tasks: xstest, strong_reject, sycophancy,
  truthfulqa, bbq, simpleqa, mask, wmdp_*, agentharm, agentic_misalignment, gdm_* suites.
- vLLM for local open-weight models (OpenAI-compatible endpoint); OpenRouter / Anthropic /
  OpenAI APIs for closed models.
- Petri / Bloom for automated behavioural audits; TransformerLens, nnsight, SAELens, repeng for
  activations, probes and steering.

## Reporting Standard
Every REPORT.md states: model ids and versions with dates; eval names with harness version and
dataset revision; n, mean, SE/CI, clustering; judge id and calibration figures; unscored
samples; elicitation details; evaluation-awareness rate where applicable; limitations; and
what would change the conclusion.
